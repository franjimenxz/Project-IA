# Evidencia P08-T02 — Provision y lifecycle

**Estado:** in_review  
**Implementación:** `implementation/P08-T02-provision`  
**Corrección (two-stage FAIL):** aislamiento HTTP de `tenant_admin`, jobs fail-closed post-disable, provision HTTP, IntegrityError por constraint, reason auditable.  
**Entorno:** local · Python 3.13.12 · PostgreSQL `ia_mcp_p02_t03`

## Resultado

`TenantOnboardingService.provision` consume un `TenantPackage` ya validado, persiste el tenant en `disabled` con config `draft`, channel mappings e `integration` refs (solo `secret_reference`/`credentials_reference`) y un audit `provision`. Replay y concurrencia sobre el mismo slug devuelven el mismo tenant sin duplicar tenant/config/mapping. `disable` cancela jobs `pending`/`claimed` del tenant, deja mappings deshabilitados, conserva auditoría (reason sanitizado en `audit_event.payload`) y no muta al tenant A. Tras disable, `SqlAlchemyJobStore.put` y `claim_due` fallan cerrado para ese tenant. No hay ingest de knowledge ni `activate`.

CLI: `python -m ia_mcp.onboarding provision|disable`. API adapter: `create_onboarding_router()` expone `POST /v1/admin/tenants/provision`, GET y disable. Principal inyectado en `app.state` (sin credenciales inventadas ni auth federada). El router sigue sin cablearse en `create_app`.

## Decisiones y desviaciones

Migración `0007_onboarding` para `integration`. `audit_event` no tenía columna `reason`; se persistió el motivo sanitizado en `payload` JSONB (`0008_audit_payload` + columna en el Table para `create_all` fresco). Segundo disable sobre un tenant ya disabled puede append otro audit `disable` (append-only). Estado y jobs permanecen idempotentes (B sigue disabled; jobs cancelled no se reactivan; A intacto).

# Evidencia P09-T02 — Open tool registry (discoverable names)

**Estado:** in_review  
**Implementación:** `implementation/P09-T02-open-registry`  
**Owner:** Core acepta los nombres que un MCP anuncia. La autorización es solo intersección de tres allowlists. `KNOWN_TOOLS` sigue exportado como set canónico de appointments; no es un mundo cerrado.

## Resultado

`available(server, tenant, skill)` es `frozenset` intersection. Un nombre presente en las tres listas se autoriza aunque no esté en `KNOWN_TOOLS` (p. ej. `crear_turno`, `appointments.delete`). Falta en cualquiera de las tres → `ForbiddenTool`.

Discovery no queda como letra muerta:

- `ContextCompiler` acepta `server_tools` inyectado. Catálogo de server ausente = set vacío = ningún tool (fail-closed). No hay fallback a `tenant_tools`.
- Allowlist vacío de skill niega todos los tools. No hay `if skill.name == "appointments"` que copie el catálogo de server.
- El skill appointments usa `TenantConfig.enabled_tools` si está presente; si no, no recorta a los seis nombres canónicos.
- FAQ y handoff siguen con set vacío.
- Evals y onboarding dejan de rechazar un nombre solo por estar fuera de `KNOWN_TOOLS`. Siguen fallando closed: overlap allowed∩forbidden, tool de skill deshabilitado, allowlists vacíos de FAQ.

`TenantContext` sigue obligatorio en boundaries tenant-scoped. No hay slugs institucionales en Core ni secretos en pruebas/logs.

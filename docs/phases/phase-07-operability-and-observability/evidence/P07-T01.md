# Evidencia P07-T01 — Telemetría correlacionada

**Estado:** in_review  
**Implementación:** `implementation/P07-T01-telemetry`  
**Rojo observado (original):** `ModuleNotFoundError: No module named 'ia_mcp.observability.propagation'`  
**Rojo review:** tests exigían `flush_telemetry`, inject en `ReminderScheduler.upsert` sin paste manual, exporter async, `set_attribute`, inbound headers ignorados.

## Resultado

- Semantic conventions 1.0.0; inject/extract W3C `traceparent` + `X-Correlation-ID`.
- HTTP público **no** adopta `traceparent`/`X-Correlation-ID` del cliente (server mint). Canal simulado autenticado sí puede adoptar correlation del caller.
- `ReminderScheduler.upsert` inyecta `payload.telemetry` (y alinea `correlation_id`) desde el contexto actual. Worker y audit usan `extract_payload`.
- Exporter async: `emit` solo encola; overflow incrementa `telemetry_exporter_dropped`; fallo incrementa `telemetry_exporter_failure` sin cambiar negocio.
- `SpanRecord.set_attribute` pasa por `span_attributes`/redact. Redactor cubre Bearer, Basic, api_key, DNI y teléfono.

## Span tree sanitizado (HTTP inbound, server-minted)

Un `GET /health/live` produce `channel.receive` con correlation/trace generados en servidor. El test de propagación afirma un único `trace_id`/`correlation_id` para `channel.receive`, `channel.send`, `scheduler.dispatch`, `mcp.resolve` y `tool.execute` **sin** reinyectar el carrier a mano después de `upsert`. Retry enlaza el span previo.
